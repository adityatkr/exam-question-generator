# Test cases

**16 test inputs** covering normal, edge and invalid cases.

## How these were run

Every case is executed by [`run_tests.py`](run_tests.py), which imports and
calls **the same functions `app.py` calls** — `validate_settings()`,
`generate_questions()`, `check_questions()`, `quality_checker.merge()` and the
four exporters. Nothing is mocked and nothing is stubbed. The `Actual output`
column below is generated by the script, not written by hand.

```bash
python tests/run_tests.py --offline   # the 9 cases that make no API call
python tests/run_tests.py             # all 16 (makes real Gemini calls)
python tests/run_tests.py --case 9 12 # selected cases
```

Raw output for every case, including the full generated questions, the
per-criterion quality scores and the token counts, is written to
`tests/output/results.json`. The table below is `tests/output/results_table.md`.

**Model:** `gemini-3.6-flash` via `google-genai`, `thinking_level` low for
generation and medium for review.

### Pass criteria

Each case has an explicit, mechanical pass rule in `judge()` in
[`run_tests.py`](run_tests.py) — a case does not pass merely because it did not
crash. For example:

- Cases 1–7 pass only if validation **blocked** the request *and* produced an
  error message (an unblocked invalid input is a failure, because it would have
  spent money on a bad call).
- Case 9 passes only if exactly 1 question came back, it is an MCQ, and the
  quality check returned a usable review.
- Case 12 passes only if exactly 20 questions came back and were all reviewed.
- Case 13 passes only if the model **refused** the gibberish source rather than
  inventing questions from it.
- Case 14 passes only if the generated question text actually contains
  Devanagari characters, not just that three questions came back.
- Case 16 passes only if all three malformed payloads are rejected with a
  specific error.

### Case design

| Group | Cases | What is being probed |
|---|---|---|
| **Invalid** | 1–8 | Input validation must block bad requests *before* an API call, so a mistake costs nothing. Empty, whitespace-only, too short, too long, zero questions, 25 questions, no type selected, unsupported upload. |
| **Normal** | 9–12 | The happy path across the range: the minimum (1 question), a typical mixed paper (5 questions, all 4 types), a bare topic with no notes at all, and the maximum (20 questions). |
| **Edge** | 13–16 | Where it should bend rather than break: gibberish source, non-English (Hindi) source, settings that conflict with each other, and malformed model output fed straight to the parser. |

Case 16 is a deliberate unit test of the failure path rather than an API call.
It feeds three bad payloads — prose-wrapped JSON, truncated JSON, and an MCQ
whose answer is not among its options — directly to `extract_json()` and
`validate_questions()`. These are exactly the conditions that trigger the
retry-once loop in the live path, and testing them directly makes that loop
verifiable without having to provoke a real malformed reply.

**16 / 16 passed.** Total wall-clock 472.9 s; the 7 API-backed cases consumed
30,160 input and 11,853 output tokens (~$0.07 at `gemini-3.6-flash`
introductory rates). Nine cases made no API call at all, which is the point of
cases 1-8: an invalid request must cost nothing.

### What the results actually show

**Validation blocks before spending (cases 1-8).** All eight invalid inputs
were rejected in 0.0 s with a specific, actionable message. Note case 2:
whitespace-only input produces the *same* message as empty input, because
`validate_settings` strips before measuring — a user who typed only spaces gets
told the box is empty, not that it is 3 characters long.

**The quality checker discriminates (cases 9-15).** Average scores were not
uniformly high, which is what makes them worth having:

| Case | Avg score | Flagged | Why |
|---|---|---|---|
| 9 — single MCQ | 10.0 | 0 | Clean, well-grounded question |
| 10 — 5 mixed types | 8.0 | — | All four types produced, difficulties spread easy/medium/hard |
| 11 — topic only | 10.0 | 0 | Works with no notes at all, just a topic string |
| 12 — 20 questions | 9.5 | **5** | **Duplicates**, not low scores (see below) |
| 13 — gibberish | n/a | n/a | **Refused** |
| 14 — Hindi notes | 10.0 | 0 | Questions in Devanagari, enums still English |
| 15 — conflicting settings | **3.0** | **3 of 3** | Bloom mismatch caught (see below) |

**Case 12 proves the duplicate detector works, and that it catches what a
static rule cannot.** All five flagged questions scored 8.0 — *above* the 7.0
threshold. They were flagged because the reviewer set `duplicate_of` on them.
Asking for 20 questions from 558 characters of normalisation notes is genuinely
too many, so the model repeated itself.

Worth being precise about what this shows: the input validator did **not** warn
here. Its heuristic only fires when more than 10 questions are requested from
fewer than 300 characters, and 558 clears that bar, so `validate_settings`
returned no warnings for this case (verified directly). The static rule missed
it and the AI reviewer caught it. That is the honest version of the argument
for module 3 — not that the heuristic and the reviewer agree, but that the
reviewer covers ground the heuristic cannot, because "is this question
substantially the same as question 4" is not something a character count can
answer.

**Case 15 is the clearest evidence that the two passes disagree usefully.** We
asked for True/False questions worth 10 marks at Bloom's level *Create* — a
specification that cannot really be satisfied, since a True/False question
cannot assess creation. Three things happened, all correct:

1. The input validator **warned** (not blocked) that this combination would
   likely be flagged.
2. The generator honoured the request but **scaled the marks from 10 down to
   2**, exactly as `generator_user.md` instructs for an indefensible
   marks/type pairing.
3. The quality checker scored all three questions **3.0/10 and flagged every
   one** for the Bloom mismatch.

A single-pass tool would have returned three confident-looking True/False
questions labelled "Create" and left the faculty member to notice. That gap is
the entire argument for module 3.

**Case 13 proves it refuses rather than hallucinates.** Given random
consonant strings as source material, the generator returned the
`unusable_source` escape hatch with the reason *"The source material contains
only random characters and gibberish with no extractable Operating Systems
content."* It produced zero questions, and the app surfaced the refusal
instead of a paper.

The escape hatch in `generator_user.md` is what gives the model a *defined*
way to decline. We have not run the controlled A/B (same gibberish, same
model, prompt with and without the clause), so we are not claiming a measured
difference here — only that the shipped prompt refuses, reproducibly, and
returns a machine-readable reason the app can act on rather than free-text
prose it would have to guess at.

**The retry loop was never needed in this run.** Every API-backed case
reported `attempts: 1` and `repaired: False`, i.e. the first reply parsed and
validated. That is the combined effect of Gemini's JSON mode (guaranteeing
syntax) and the explicit schema in the prompts (guaranteeing shape). The retry
path is therefore exercised directly by case 16 rather than left untested.

**Exports were generated for every passing API case**, and their byte sizes
scale sensibly with the paper: case 12's answer-key PDF is 10,199 bytes against
case 15's 3,836.
